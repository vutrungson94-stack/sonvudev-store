# WORKFLOW.md — enterprise release workflow for SonVuDev Store

This file defines **how every change ships**. It is versioned and audited.
When reality and this file disagree, reality does not silently win — update this file first, with the reason.

## 0. Before anything

1. Read `AGENTS.md` invariants.
2. Identify the **exact commit** this change builds on. Never start from memory of "latest".
3. List the files you expect to touch. More than 5 files = stop and get explicit approval.

## 1. Analyze phase — no edits allowed

- Read changed commit(s) since last release: `git log --oneline -5`, `git diff <last-release>`.
- Find the **root cause**. The failing symptom (e.g. a 308 on `/`) is never the root cause; it is always two or three commits of drift upstream.
- For quality/maturity work, perform a codebase-grounded audit per `AGENTS.md §4.1`: scan relevant files and flows for hardcode (keep non-dynamic hardcodes), orphans (remove only if inappropriate), duplication/reuse, cross-platform/multilingual independence, and evidence for CMMI L5/platform maturity.
- Write the analysis down in the commit message or `docs/` — never in your head.

## 2. Baseline gate

Run and record:

```powershell
npm run lint; npm run audit; npm run case; npm run workflow
npm test
npm run build
```

If anything is red **before** you touch anything, record it. Your change must leave at least as green as it found.

## 3. Design gate — `.github/change-plan.yml`

Fill in the template (see `docs/CHANGE-PLAN.md`):

- `task` — one sentence, imperative.
- `scope` — files, with line ranges for the behavior.
- `why` — the failure this fixes, with the actual log line.
- `invariants_checked` — which invariants from `AGENTS.md` touch this change and how they were preserved.
- `tests` — tests that already covered it / new tests to add / test changes and why they are correct.
- `risk` — what breaks if this is wrong, and how it is caught.

No plan = no edit.

## 4. Implement

- Smallest possible change that makes the failing test/repro pass.
- No refactoring opportunism. If you see a dead branch unrelated to the task, log it and move on.
- Formatting is `npm run css:minify` for the stylesheet (there is no `npm run format`; the source of truth for CSS is `public/styles.css` and the browser loads `public/styles.min.css`).

## 5. Fix-until-green — the rule that is never relaxed

For every gate you fail after your change:

1. Read the failure **as written** (file, line, actual output).
2. If the failure is in a file you did not touch: your change broke an assumption — revert your change to the part that matters or remake it.
3. If the failure points at a test being wrong: prove it by checking the test file first; only then touch the test, and only with a reason.
4. Never disable, skip, or `.skip` a test. Never lower a workflow's confidence level.
5. If the same red persists after two different attempts, that is the signal the approach is wrong — back the change out and take a different one.

## 6. Verify phase

- All gates re-run green.
- `npm run build` produces `publish-output/node` clean.
- If the change touches routing/payment/legal/i18n: `npm run seo:check -- https://sonvudev.com` must be green against the live site after deploy. If you cannot verify live, say so explicitly — do not claim it works.

## 7. Build & sync

```powershell
_Tests/gtest.ps1 -Project . -NonInteractive
_Build/gbuild.ps1 -Project . -NonInteractive
_Sync/gsync.ps1   -Project . -DryRun        # then -Yes when clean
```

`_Build` runs `npm run build` + `npm test` + security/policy scan offline. `_Sync` commits and pushes only after the build is green.

## 7.5. Pre-sync check — no-regress list (mandatory)
Before `_Sync`/push you MUST read this list. Anything on it is a past production incident; reverting it re-opens that incident.
- **Stylesheet loading:** the stylesheet travels **inside the page**. `src/lib/inline-styles.mjs` reads `public/styles.min.css` and replaces the `<link rel="stylesheet">` with the CSS itself, so there is no render-blocking request at all and nothing arrives late to shift the layout. The source templates keep the plain `<link>` (that is what the audit checks, and what a checkout without a build falls back to), and the rendered page carries `<style id="site-styles">`. **Never** `<link rel="preload" as="style">` + `css-ready.js` defer: that pattern painted unstyled HTML first and jumped → CLS ~0.5.
- **The stylesheet is one file, generated:** source is `public/styles.css`; the browser loads `public/styles.min.css` built by `scripts/minify-css.mjs`; the page inlines that built file. Never hand-edit `styles.min.css`; edit the source and regenerate. `build-web.mjs` runs minify before the required-file gate.
- **Minified pipeline:** source is `public/styles.css` (what tests/audit assert on); browsers load `public/styles.min.css` generated by `scripts/minify-css.mjs` on `npm run build` / `npm run css:minify`. Never hand-edit `styles.min.css`; edit the source and regenerate. `build-web.mjs` runs minify before the required-file gate.
- **Minified JavaScript:** `public/app.js` and `public/i18n.js` stay readable in the source tree (the audit, the metrics and the tests read them as text) and are minified into the artifact by `scripts/minify-js.mjs` (esbuild, identifiers not renamed). Never hand-edit the artifact copy. **The deploy must serve the artifact, not the working tree:** `render.yaml` runs `npm ci --include=dev && npm run build` and starts `publish-output/node`, whose `src/app.js` resolves `publicDir` to the minified `publish-output/node/public`. A deploy that serves the working tree ships the unminified source — Lighthouse charges "Minify JavaScript" for it, and no local gate catches it, because the local Lighthouse run measures the artifact on localhost. `npm run seo:check` fails when a live `/app.js` or `/i18n.js` is within 10% of the source size. Do not revert `buildCommand` to `--omit=dev` (the build needs esbuild) or `startCommand` to the repo root.
- **The web app manifest is injected after load, not linked in the head.** A `<link rel="manifest">` in the head is discovered while the HTML is parsed and fetched as a high-priority request, which puts it on the critical request chain (Lighthouse "Network dependency tree": 781 ms for a 1 KiB file). `public/quality.js` adds it from a deferred script instead. Do not move it back into `ICON_LINKS`; the install prompt still finds it a few hundred milliseconds later.
- **"Reduce unused JavaScript" of ~443 KiB is a browser extension, not the site.** The URL is `chrome-extension://…/bubble_compiled.js` (Google Translate). `scripts/lighthouse-check.mjs` already runs `--disable-extensions` and only fails on first-party unused JS. Do not "fix" this by removing site code; re-run headless.
- **Contrast ink:** text on light surfaces must use `--coral-ink: #b81e14` (6.14:1 on paper), never `--coral: #ff765b` (2.48:1). `--coral` stays for decorative fills/dots/borders. Small grays and status pills must stay ≥4.5:1 (use `#1f2d36` for muted/small text). Buttons: `.button-primary span` uses `var(--brand-mist)` (on dark gradient), coral-filled buttons use `var(--coral-ink)` background with white text.
- **Fonts:** fonts are **self-hosted** in `public/fonts/*.woff2` and declared with `@font-face` at the top of `public/styles.css`. **Never** reintroduce `fonts.googleapis.com`/`fonts.gstatic.com`: the stylesheet they served was a render-blocking request to a second origin and cost ~260 ms. `font-display: optional` everywhere (`swap` caused CLS 0.357 from late font replacement) — the product page used `swap` and was corrected.
- **Body font:** `Be Vietnam Pro`, not DM Sans. DM Sans ships only latin/latin-ext, and latin-ext stops at U+1E9F — the Vietnamese block (U+1EA0-1EF9) is not in it, so every accented character in the body copy fell back to Arial while the rest stayed in DM Sans. The audit checks that `styles.css` declares `@font-face` for both brand families; a font without a Vietnamese subset fails that check rather than silently falling back.
- **Cache:** `express.static` is `maxAge: "1y"` for static assets. HTML pages are `max-age=300` (rendered, not fingerprinted). Do not lower static cache to 5m.
- **Asset versions:** every CSS/JS/font the pages load is versioned by the **hash of its own bytes**. The build writes `public/asset-manifest.json` into the artifact and rewrites the packaged HTML; `src/lib/assets.mjs` reads the same manifest when rendering pages at request time. A page and the file it points at must never be able to disagree.
- **Test env contract:** every `*.test.js` MUST import `./helpers/env.mjs` first. `test/env-contract.test.js` scans all test files and fails the whole `checks` job if one is missing.
- **Font subset order:** in `public/styles.css`, the `vietnamese` `@font-face` of each family must be declared **LAST**. The vietnamese and latin-ext subsets cover some of the same characters (ư đ Đ ơ ă Ư ũ and the dong sign ₫), and when two faces of one family cover a codepoint the browser uses the one declared last. With the order reversed the browser fetched a 20 KB `space-grotesk-latin-ext.woff2` that no character on the page needed, and that file sat on the critical path. `test/pwa-and-fonts.test.js` fails if the order is wrong or a rule is declared twice.
- **Font preloads:** exactly four, all `crossorigin`, **on every page** (the static templates, the product page and the blog pages): `be-vietnam-pro-latin`, `be-vietnam-pro-vietnamese`, `space-grotesk-latin`, `space-grotesk-vietnamese`. They are the files a Vietnamese page uses, and preloading them takes the fonts off the "CSS → font" hop. A page that does not preload them discovers them only when the browser reaches the `@font-face` rules — the blog pages were rendered in code and had no preloads at all, and their fonts arrived a third of a second after the HTML.
- **A page must fetch only the four subsets the shop ships.** `be-vietnam-pro-latin`, `be-vietnam-pro-vietnamese`, `space-grotesk-latin`, `space-grotesk-vietnamese`. There is no `latin-ext` face, on purpose: with one declared, the browser downloads it (14 KB and 19 KB) while it looks for a character nothing on the page needs — and it downloads it late, so it lands at the bottom of the network tree as the critical path's deepest node. `npm run lighthouse:check` fails when a page fetches a font file outside the list.
- **A Latin character outside those two subsets fails the build.** `test/font-coverage.test.js` scans the catalogue, the blog posts and the page templates. A character it does not cover (a Turkish dotted I, a Latin Extended letter) would render in the system face instead of the brand one, so it is reported at the source rather than discovered on a phone. Non-Latin scripts (Japanese, Chinese in the blog posts) are the reader's system font by design and are not the shop's business.
- **No link inside a link:** the product page's header must close `</a>` after the wordmark, before the navigation. A link inside a link makes the HTML parser re-create the outer link **empty** inside the `<nav>` — a nameless link that axe reports as "Links do not have a discernible name" and Lighthouse as a malformed accessibility tree. `test/product-header-links.test.js` holds the shape.
- **Landmarks:** the announcement bar is an `<aside>` (it is the only content outside the header, and content outside every landmark is unreachable for anything that navigates by landmark); the buy card is a `<div>` (an `<aside>` inside the banner is two regions overlapping — axe `landmark-complementary-is-top-level`).
- **Heading order:** no skipped levels. The blog index titles are `h2` under the page's `h1`, not `h3`.
- **The server renders the related products; the client does not fetch them again.** `public/related.js` returns when its box already holds links. It used to fetch the whole catalogue (14 KB, 549 ms) to replace a list the server had already rendered, and that fetch was the longest chain on every product page. The 404 page, whose list is empty, still needs it.
- **Analytics: none from anyone else.** The page loads **no third-party script at all**. Cloudflare Web Analytics was 10 KB of legacy JavaScript with a one-day cache TTL; GA4's `gtag.js` is blocked outright by every tracker blocker (the visitor's own network tab showed `ERR_BLOCKED_BY_CLIENT` on every page) and collects nothing for those visitors. The shop measures itself instead: `public/quality.js` → `/api/quality` on the same origin with `navigator.sendBeacon`, so it survives the visitor leaving the page and no proxy or blocker can stop it. Putting either tag back is one tag plus one CSP entry; what it costs is written down in `docs/QUALITY-L4-L5-BACKLOG.md`.
- **PWA screenshots:** the manifest carries one `wide` and one `narrow` screenshot, and Chrome warns in DevTools when one is missing. They are real screenshots of the storefront, taken by `scripts/make-pwa-screenshots.mjs` (a browser with device emulation — a resized desktop window is a desktop page in a small frame).
- **Categories are canonical, never printed raw.** The catalogue's category is typed by hand in the admin panel, so it can arrive as "Utility" (English, singular) beside "Tiện ích". The raw value is mapped onto the canonical list in `src/lib/categories.mjs`, where the catalogue is read — so the filter row groups them as one, labels them "Tiện ích", and the browser translates that in all eight languages. The Chinese homepage once read "全部 | 工具 | 实用工具 | Utility": one filter in English among three translated ones. A category that matches nothing canonical is shown exactly as the owner typed it — honest, and still worth fixing in the catalogue.
- **The seeded catalogue uses canonical categories** (`src/store.js`): a demo install must show the same filters as the real shop.
- **Chrome of a page belongs to the page's frame.** The blog's two buttons (home, language) share the 720px column the blog's text is set in — not the screen width, not the storefront's 1160px. A nav that spans the screen while the text is centred reads as two unrelated things.
- **Before sync, if your change touches any of the above files:** update this list first, in the same commit, with the reason. Reviewers must check the list matches the diff.
- **Measure on the live site, not on a local server.** Lighthouse run against `localhost` measures the local setup (no compression, no CDN, sometimes no catalogue) and its numbers are not the site's numbers: the same build measured CLS 0.22 locally and 0 on the deployed site, and the render-blocking finding does not appear at all locally while it does appear for a visitor on a slow link. The local run is for catching regressions; the deployed run is the truth. `npm run lighthouse:check -- <url>` runs the same checks against any URL.
- **Lab is not field.** The DevTools "Local metrics" panel is a laboratory reading: if Lighthouse runs on a page that is already loaded, it reports the previous load's paint (LCP 0.08 s) — the panel says so itself ("Reload the page for accurate LCP"). The number that decides anything is the p75 of real visits, and the site's own field data is the beacon in `public/quality.js` → `/api/quality`. Read it with `npm run quality:report -- <log>`: the script compares each p75 against web.dev's "good" line, exits non-zero when one is over, and appends a reading to `metrics-quality-trends.json` so the field data becomes a series instead of an anecdote.
- **Canonical URL / trailing slash.** Every page has exactly one canonical address: `/x` (no slash) except locale roots, which are `/en/`. `/x/` answers **308** to `/x`; `/en` and `/en/` both answer 200 (both are registered routes, canonical `/en/`). Every `/?buy=<id>` link carries `rel="nofollow"` — it serves the homepage bytes under a query string, so a crawler must not treat it as a second homepage. `test/trailing-slash.test.js` holds the shape; changing it re-opens the GSC "trang trùng lặp" report. See `docs/ADR/0001`.
- **Coverage is a gate.** `npm run coverage` runs the suite with `--experimental-test-coverage` and fails below lines 70% / branches 60% / functions 70%. Measured at the thresholds' introduction: 89.3% / 73.2% / 81.5%. Do not lower the thresholds to make a change pass — raise the tests instead.
- **A metric that is not measured is `null`, not `0`.** `scripts/metrics.mjs` used to coerce a missing value to `0`, which reported a perfect escape rate and an instant lead time on a project that had measured neither. A `null` is skipped in the baseline comparison and printed as "chua do duoc". Never reintroduce `?? 0` for a measurement.

## 8. Post-release

- Watch `checks.yml` — specifically the `deployed-site` job, which now polls `/api/health` for the commit sha before auditing.
- If the deploy is red:
  1. `git revert <released-sha>` — preferred — `git revert` is non-destructive and leaves a clear history.
  2. Do not cherry-pick partial fixes into the live branch while the health check is failing.
  3. Write a postmortem in `postmortems/YYYY-MM-DD-<slug>.json`.

## 9. Emergency changes

If something is actively burning:

- Revert to last green on `main` with `git revert` rather than patching forward under pressure.
- Apply the emergency fix only if revert is impossible or makes it worse. Emergency fixes still get a full postmortem and a gate-run in the same session.
